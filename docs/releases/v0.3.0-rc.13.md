# v0.3.0-rc.13

This release candidate aligns Breakglass OIDC identity mapping with Kubernetes
and keeps the requester identity and notification email separate from the
username used to authorize access on a target cluster. It also updates Go,
frontend development, and CI dependencies.

## OIDC identity mapping

- IdentityProvider and ClusterConfig support arbitrary string-valued username
  claims and literal prefixes. A cluster can inherit its provider's mapping,
  override it, or explicitly disable an inherited prefix with an empty string.
- `spec.kubernetesIdentity` supports Kubernetes claim mappings for username,
  groups, UID, and extra fields, plus CEL claim and user validation rules.
  Breakglass now uses the upstream Kubernetes OIDC authenticator and validation
  instead of its custom JWT/JWKS verifier.
- Provider configuration supports additional accepted audiences, signing
  algorithms, a separate discovery URL, and private CA trust. Cluster mappings
  cannot change the provider's token-verification trust or replace the provider
  groups used by Breakglass authorization.
- New sessions persist requester provenance and email independently from
  `spec.user`. Ownership checks, approval controls, rate limiting, and UI actions
  support authenticated principals without an email address. Notifications use
  the persisted requester email, not the mapped Kubernetes username.

For a Kubernetes principal such as `tdi_security_oidc:k834798`, configure the
target ClusterConfig alongside its usual connection settings:

```yaml
spec:
  userIdentifierClaim: preferred_username
  userIdentifierPrefix: "tdi_security_oidc:"
```

The provider can still supply `email: christos.ntogkas@telekom.com` for
notifications. See the [mapping, email, and migration guide](../oidc-compatibility.md)
for complete examples and structured policies. These changes are in
[PR #1523](https://github.com/telekom/k8s-breakglass/pull/1523).

## Upgrade guidance

1. Apply the release CRDs before configuring the new fields, then upgrade the
   controller and frontend together.
2. Match the target API server's complete username. Prefixes are literal and
   include their separator. Translate `--oidc-username-prefix=-` to an explicit
   empty prefix; configure `issuerURL#` explicitly if the API server uses that
   implicit prefix. Breakglass does not silently add it to existing configs.
3. Configure the identity provider to include the standard `email` claim in the
   bearer token sent to the Breakglass API. Requesting the `email` scope alone
   is insufficient if email appears only in an ID token or UserInfo response.
   Breakglass does not call UserInfo or derive email from a mapped username.
   Email-domain restrictions still require an email claim, and requester
   notifications are skipped when no usable email is present.
4. Use either shorthand claim/prefix fields or a structured policy on a given
   resource. A cluster structured policy replaces the provider mapping policy
   as a whole. Keep provider and target-cluster claim semantics consistent.
5. Existing sessions are not rewritten. Recreate a session whose target
   username was wrong when it was requested. Legacy sessions with no provider
   provenance retain only the trusted single-provider compatibility path;
   partial provider provenance fails closed.

For an `email` username claim, upstream Kubernetes accepts an absent
`email_verified` claim but requires Boolean `true` when it is present. To
require explicit verification, configure a provider claim-validation expression
such as `claims.?email_verified.orValue(false) == true`. Breakglass continues to
require token expiration and reject future issued-at timestamps.

Charts accompanying this candidate are **escalation-config 0.4.6** and
**debug-session-catalogue 0.2.9**, both packaged with appVersion
**v0.3.0-rc.13**. The catalogue values interface is unchanged; release packaging
supplies verified utility image digests. Pin deployed images by immutable digest.

## Security and validation

Provider and issuer scope remain part of session ownership. Prefixes and CEL
expressions are never reversed to infer ownership. Plain-SMTP notifications use
gomail's MIME encoder, with notification tests decoding transfer encoding before
checking content.

Regression coverage includes all nine supported asymmetric signing algorithms,
mapping precedence, missing and malformed claims, CEL validation, discovery and
JWKS failures, key rotation, cache concurrency, no-email identities, and
provider-scoped ownership. Real single-cluster and multi-cluster tests require
denial before approval, authorization of the exact prefixed principal afterward,
and denial of the unprefixed username and email.

The frontend audit reports five existing high-severity findings in the
braces/micromatch/globby/stylelint tooling chain, with no fix reported by the
scanner. Frontend vulnerability findings remain advisory under the repository's
release policy; scanner failures and other security gates remain blocking.
This candidate does not claim deployed production acceptance or exhaustive
coverage of every possible JWT or CEL input.
